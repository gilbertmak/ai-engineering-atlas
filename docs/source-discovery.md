# YouTube source discovery

`bun run discover:sources` uses the official YouTube Data API v3 only from a trusted CLI or worker environment. Set `YOUTUBE_DATA_API_KEY` there only: never use a `VITE_` name, commit it, log it, or put it in a browser URL. Restrict the key to YouTube Data API public-metadata access in Google Cloud.

The default source is the official `@aiDotEngineer` uploads playlist. Set `YOUTUBE_DISCOVERY_UPLOADS_PLAYLIST_ID` to bypass channel resolution, or `YOUTUBE_DISCOVERY_CHANNEL_ID` / `YOUTUBE_DISCOVERY_CHANNEL_HANDLE` to select another approved source. The worker resolves a channel when needed and persists the uploads playlist ID so later runs skip that request. It pages through `playlistItems.list` at 50 records per page, then calls `videos.list` in 50-ID batches. It deliberately makes no `search.list` calls. Every API request is paced (default 250 ms minimum separation); transient network failures and `429`/`5xx` responses use bounded exponential retry, while other HTTP errors fail closed.

State defaults to the ignored `data/youtube-discovery-state.json`. Normal runs stop when the previously saved newest upload is reached, retrieve only newly observed IDs, and preserve the newest ID as the next high-water mark. `bun run discover:sources --full` paginates the entire approved playlist for reconciliation. Current fixture IDs are always treated as known. Output includes `source: youtube-data-api-v3` and `fallback: none`: legacy HTML/oEmbed discovery is intentionally not an automatic fallback.

Discovery produces candidates only. It does not update the public fixture catalog or bypass title/channel identity review.

Each run atomically writes a private candidate handoff at `data/youtube-discovery-candidates.json` (or `YOUTUBE_DISCOVERY_CANDIDATES_PATH`). Its only state is `review_required`; the public `/v1/catalog` API never reads it. A reviewer/Hermes publication process must create a new reviewed projection before a candidate can appear in the Atlas.

`bun run discover:sources:scheduled` is deliberately disabled unless the private worker environment sets both `ATLAS_DISCOVERY_SCHEDULE_ENABLED=true` and `ATLAS_METADATA_AUTO_PUBLISH_ENABLED=true`. It writes the candidate audit handoff, then creates an atomically replaced catalog projection only for `new` records whose exact channel and uploads playlist match `ATLAS_APPROVED_YOUTUBE_CHANNEL` and `ATLAS_APPROVED_UPLOADS_PLAYLIST_ID`. Those records remain `metadata_only` and unclassified; no insight or attribution is created. This is a configuration gate, not a scheduler: Delivery Operations owns the daily launcher, secret injection, quota monitoring, and approval to enable it. No live API call is made by this repository without a server-side `YOUTUBE_DATA_API_KEY`.
